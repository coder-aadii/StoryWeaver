# Migrations

> How schema changes are made with Alembic.

## Status

Implemented. One migration exists: `5d669179817c_initial_schema`.

## Setup facts

- `alembic/env.py` takes the URL from `get_settings().database_url` (env `DATABASE_URL`), imports `app.models` so tables register, and uses `Base.metadata` as target.
- `alembic.ini` has no URL on purpose.
- The first migration was hand-edited after autogeneration: it imports `pgvector.sqlalchemy` and begins `upgrade()` with `CREATE EXTENSION IF NOT EXISTS vector`. Autogenerate does **not** create extensions, so any fresh database needs this to run through migrations (the Docker init script also creates it).

## Workflow

```bash
make db-revision m="add character versions"   # autogenerate
# review the file: autogenerate misses extensions, server defaults, some index options
make db-migrate                                # upgrade head
cd apps/api && uv run alembic check            # expect: No new upgrade operations detected
cd apps/api && uv run alembic downgrade base && uv run alembic upgrade head   # prove reversibility (dev DB only)
```

## Rules

1. Always review autogenerated output; add `import pgvector.sqlalchemy` if a `Vector` column appears.
2. Make `downgrade()` work; the test fixture runs `downgrade base` then `upgrade head`.
3. Never edit a migration that others may have applied; add a new one.
4. Data backfills belong in the migration or a separate idempotent script — Decision pending.
5. Changing the embedding dimension requires a migration plus re-embedding ([embeddings and vector search](../data/embeddings-and-vector-search.md)).
